# 07 · 架构决策记录（ADR）

格式：一条决策 = 背景 / 选择 / 后果。状态：`已定`、`待定`、`已废弃`。

---

## D1 · 三层角色与命名

**状态：已定**

- 恒星 **Star**：家中服务器，唯一数据权威。
- 行星 **Planet**：公网无状态中继；对**原生流量**内容零知识；同时作为 Web 的 HTTPS 网关（可见 Web 明文）。
- 卫星 **Satellite**：原生客户端（桌面、Android）与 Web 客户端（浏览器）。

**后果**：所有文档、模块 ID、日志、指标统一使用这三个词；不再引入第四种运行时角色。提到「零知识」时必须限定为「原生流量」。

---

## D2 · 中继传输：WSS + 自研帧

**状态：已定**

**背景**：恒星在 NAT 后，需要主动拨出；卫星在外需要经公网中继；要支持多路复用、背压、大文件。

**选择**：外层使用 WSS（TLS 1.3）+ 自研长度前缀二进制帧；行星只做流级别转发。

**后果**：

- 穿透 HTTP 代理友好；Kotlin 两端统一。
- 需要自己实现并测试流控、保活、重连、公平性。
- 不使用 HTTP/2 或 gRPC，避免行星理解应用语义。

**备选**：WireGuard/Tailscale 打底（放弃，因需要自定义鉴权与零知识中继）；HTTP/2 over tunnel（放弃，行星会看到更多元数据且实现复杂）。

---

## D3 · 原生端到端加密与行星零知识（仅原生）

**状态：已定**

**背景**：行星是公网服务器，可能被攻破；原生客户端的家庭数据不能托付给它。

**选择**：恒星↔原生卫星在一条外层流上建立独立的内层会话；Tink Ed25519 双向认证 + HybridEncrypt 密钥封装 + AES-256-GCM 逐帧加密。

**后果**：

- 行星只能看到原生流 ID、大小、时序。
- 握手与重放保护是安全关键路径，需评审与负例测试。
- LAN 直连也走同一内层会话，保持单一代码路径。
- Web 路径不走内层会话，见 D21/D22。

**备选**：行星对所有流量终止 TLS（否决，原生失去零知识）；自研 Noise（否决，密码学实现风险）。

---

## D4 · SQLite + 薄 JDBC 数据层

**状态：已定**

**背景**：家庭规模数据；需要单文件、易备份、可动态加模块。

**选择**：SQLite（WAL）+ `sqlite-jdbc` + 宿主 `Db` 门面；模块声明 SQL 迁移；不使用 ORM/代码生成。

**后果**：

- 一个 DB 文件 + 附件目录即可备份。
- 单写者；写事务必须短。
- 动态模块无需重新生成宿主代码；迁移由宿主执行。
- 类型安全靠 DTO 映射与测试，不靠编译期 SQL 检查。

**备选**：Exposed/SQLDelight（放弃，动态模块与聚合 schema 不便）；PostgreSQL（放弃，运维成本）。

---

## D5 · 模块 = 服务端 + 客户端代码包

**状态：已定**

**背景**：功能需要可安装；客户端 UI 也要动态。

**选择**：`.hmod` 包含服务端 JAR、桌面 JAR、Android DEX、assets、manifest、签名；服务端与客户端都通过 SPI 注册。

**后果**：

- 真正的动态 UI 能力，不受声明式 DSL 限制。
- Android 动态代码政策/版本耦合/无法沙箱。
- 模块必须与宿主 Compose/Kotlin 版本兼容。
- 卸载/升级在 Android 上需要重启进程。

**备选**：服务端驱动 UI（放弃，表达力受限）；仅服务端模块（放弃，不满足需求）。

---

## D6 · 客户端平台：桌面 + Android + Web

**状态：已定**

**选择**：原生端用 Compose Multiplatform 共享 UI（桌面 JVM + Android ART）；Web 端用固定 TypeScript/HTML/CSS 壳；不包含 iOS。

**后果**：

- 原生 UI 与业务代码共享；Web 页面单独维护（固定壳）。
- 平台能力（相机、文件、通知、密钥存储）需要 `expect/actual` 或接口注入。
- Web 不共享 Compose 代码，只共享 RPC/JSON 契约。
- iOS 需要时再评估，不阻塞 v1。

---

## D7 · 拓扑权威在恒星

**状态：已定**

**背景**：卫星需要知道 LAN 地址与行星列表；行星可能多个。

**选择**：恒星保存并签发拓扑；原生卫星缓存；行星只保留在线注册表；Web 使用当前行星的 HTTPS 网关，不缓存拓扑。

**后果**：

- 单一事实源，冲突少。
- 恒星长期离线时，原生卫星只能使用过期缓存；需要合理 TTL 与手动地址兜底。
- 行星不需要业务数据库。
- Web 地址由行星决定；切换行星时浏览器需换 URL。

---

## D8 · 附件内容寻址

**状态：已定**

**选择**：`files/sha256/ab/cd/<hash>` + 引用表 + GC；DB 只存相对 key。

**后果**：

- 自动去重、完整性校验、备份简单。
- 需要引用表与两阶段 GC；删除业务记录时必须在同一事务删引用。
- 大文件流式处理，不进 DB。

---

## D9 · v1 在线优先

**状态：已定**

**背景**：离线优先与 CRDT 会显著增加复杂度。

**选择**：业务数据以恒星为准；原生卫星只缓存壳数据（拓扑、模块、设置）；Web 不缓存业务数据；无网时展示错误/只读缓存。

**后果**：

- v1 实现简单、一致性强。
- 移动端弱网体验有限；后续可加离线缓存与冲突合并。
- RPC 设计保留幂等键与版本号，为未来同步留余地。

---

## D10 · 模块签名 + 恒星背书

**状态：已定**

**选择**：发布者 Ed25519 签名 `.hmod`；恒星维护信任库；恒星向卫星签发 `ModuleAttestation`。

**后果**：

- 卫星只需信任恒星，不必维护发布者列表。
- 恒星是模块信任的根；恒星被攻破则模块供应链也失守。
- 需要密钥轮换与撤销流程。

---

## D11 · 技术栈与依赖策略

**状态：已定（版本在 M0 锁定）**

**选择**：Kotlin 2.4.x、JDK 25（JVM）、Gradle 9.7.1、Ktor（WSS + HTTPS 网关）、kotlinx.*、Tink 1.7.x、Argon2id（Web 密码）、sqlite-jdbc、Compose Multiplatform/AndroidX Compose、JUnit 5；Web 用 TypeScript 5.x + 原生 HTML/CSS，`tsc` 构建。

**后果**：

- 现代开发体验与跨平台共享。
- 依赖数量高于「纯标准库」路线；需要版本锁定与供应链审查。
- 不引入 DI/ORM/通用 Web 框架，控制复杂度；Web 零运行时依赖。

---

## D12 · 模块 API 稳定面

**状态：已定**

**选择**：`core:star-api`、`core:client-api`、`core:ui` 是唯一稳定 API；从 M1 起主版本冻结；只做兼容新增。

**后果**：

- 第三方模块可长期使用。
- 宿主内部重构自由，但不能泄漏到 API。
- 破坏性变更需要升主版本并保留过渡期。

---

## D13 · Git 与提交规范

**状态：已定**

**选择**：遵循上级 `RULES/COMMIT.md`：

- 原子提交，一项一个 commit。
- 格式 `<括号><动作><括号> <摘要>`：大 `{}`、中 `[]`、小 `()`。
- 每个 commit 后推送 `origin/master`。
- 不 amend、不强推、不改写已推送历史（除非明确要求）。

**后果**：历史可读、可回滚；CI 可按提交粒度追溯。

---

## D14 · 版本策略

**状态：已定**

- **宿主**（star/planet/satellite）：`0.<minor>.<build>`；Android `versionCode` 单调递增。
- **模块**：独立 SemVer（`MAJOR.MINOR.PATCH`）。
- **API**：整数主版本（`api.star` / `api.client`）。
- **协议**：整数主版本 + 次版本（`protoMin/protoMax`）。

**后果**：模块与宿主解耦；升级矩阵需要测试；发布页必须列出兼容范围。

---

## D15 · 不引入 ORM / DI 框架

**状态：已定**

**选择**：手写 SQL + 构造函数注入 + 显式装配。

**后果**：

- 依赖少、启动快、动态模块边界清晰。
- 重复代码略多；用小型宿主工具与约定降低样板。
- 模块不能依赖宿主 DI 容器。

---

## D16 · Android 动态加载方式

**状态：已定（需 spike 验证）**

**选择**：`InMemoryDexClassLoader`（API 26+）+ `d8` 产物；父加载器提供宿主 API/Compose/Tink。

**后果**：

- 避免可写目录执行代码限制。
- ART 无法卸载类；升级/卸载需重启进程。
- 不允许 Android 资源、manifest 组件、原生库。
- Play 政策限制；自有渠道分发。

**备选**：Play Feature Delivery（若上架 Play）；内置模块 + 服务端驱动 UI（保底）。

---

## D17 · LAN 也启用端到端会话

**状态：已定**

**选择**：原生卫星的直连与中继都跑同一内层会话；Web 不适用。

**后果**：

- 单一代码路径；局域网防窃听。
- LAN 上多一层加密开销（家庭规模可忽略）。
- 调试时需要工具解密或使用开发模式日志（不打印密钥）。
- Web 走 HTTPS 网关，不经过内层会话。

---

## D18 · 模块间不共享数据库表

**状态：已定**

**选择**：不建跨模块外键；用逻辑 ID + RPC/事件协作；表名带模块前缀。

**后果**：

- 模块可独立卸载。
- 跨模块一致性由应用层保证；需要定期完整性检查。
- 复杂查询可能需要在宿主层聚合。

---

## D19 · v1 单家庭、单恒星

**状态：已定**

**选择**：一个原生卫星配对到一个恒星；Web 登录到一个 `homeId`；不实现多家庭切换。

**后果**：

- 数据模型与 UI 简化。
- 为未来多家庭保留 `homeId` 与拓扑结构；后续可扩展。

---

## D20 · 模块 v1 限制

**状态：已定**

**选择**：模块不支持原生库、Android 资源、manifest 组件、后台常驻服务、模块间代码依赖、多版本并存；Web 不加载模块，也没有模块自定义页面。

**后果**：

- 降低动态加载与安全风险。
- 复杂能力由宿主提供（相机、文件、通知等）。
- Web 只能使用宿主固定页面；动态模块只影响服务端与原生 UI。
- 未来按需求逐项放开，并补安全评估。

---

## D21 · Web 卫星：行星 HTTPS 网关 + 固定壳

**状态：已定**

**背景**：需要不安装客户端就能访问；浏览器不适合承载 Tink 端到端会话，也不适合动态代码包。

**选择**：

- Web 是完整卫星（可浏览/编辑业务数据）。
- 行星提供 HTTPS 网关，把浏览器请求映射为恒星隧道上的 `WEB_HTTP` 流。
- 恒星提供固定 TypeScript/HTML/CSS 壳与 `/api/web/v1/*` JSON RPC；不加载 `.hmod`。
- 账号密码 + 服务端会话（HttpOnly Cookie）+ CSRF；首次管理员由原生卫星创建。

**后果**：

- 零安装，任何现代浏览器可用。
- 行星终止 TLS，**可见 Web 明文**（见 D22）。
- Web UI 固定；动态模块只有服务端与原生 UI。
- 需要 CSP/CSRF/限流/会话管理/日志脱敏。
- 复用同一套 RPC、权限与业务逻辑。

**备选**：每家庭自建公网 HTTPS（否决，NAT/证书/运维复杂）；浏览器端 E2E（后续评估，密钥管理与体验复杂）；服务端驱动 UI（否决，表达力不足）。

---

## D22 · Web 信任降级：不承诺行星零知识

**状态：已定**

**背景**：HTTPS 网关必须在行星终止 TLS 才能转发 HTTP。

**选择**：明确接受 Web 路径的行星可见明文；原生路径继续零知识；行星不记录正文/Cookie/Authorization；Web UI 提示；高敏感操作建议原生。

**后果**：

- 威胁模型分原生/Web 两条；文档与 UI 不能笼统宣称「行星零知识」。
- 行星被攻破时，Web 数据与会话暴露；原生数据不受影响。
- 需要隐私说明与用户预期管理。
- 后续若做 Web E2E，需单独立项。

**备选**：禁止 Web（否决，不满足需求）；所有流量都走 Web 网关（否决，原生失去零知识）。

---

## D23 · 业务模块文档结构

**状态：已定**

**选择**：

- 一个模块一个文件：`docs/modules/<module-id>.md`；超过 2 页再拆同名文件夹。
- 跨 2 个以上模块的流程放 `docs/flows/`，不塞进模块卡。
- 修改 RPC、表结构或权限时，必须同步更新对应模块卡。
- 模块注册表先用 Markdown 表；M1 后再评估 YAML + CI 校验。
- 模块卡固定包含：目的与非目标、场景、边界、领域模型、权限、RPC/事件、原生/Web UI、数据与迁移、验收、开放问题。

**后果**：

- 模块文档有统一入口与模板，新增模块不依赖口头约定。
- 模块卡只写当前契约；历史取舍仍进 ADR。
- 首批模块卡为 `locations`、`inventory`、`documents`、`tasks`，其余进入路线图时再写。

## D24 · 位置使用多根森林

**状态：已定**

**背景**：家庭位置不只一个「家」。异地恋、老家、工作地会同时存在，单根会把它们强行塞进同一棵树，语义和 UI 都别扭。

**选择**：

- Level 0 允许 0..N 个 `site` 根节点（自己家、老家、工作地、异地恋的住处等）。
- 根之间平级，按 `sort` 排序；v1 根只能重命名、排序、归档，不能挂到其他根下。
- 物品选择器按 Level 0 地点分组；同名房间不冲突。
- 地点之间的物品转移由 `inventory` 的流水记录，`locations` 不存移动历史。

**后果**：

- 需要地点切换器与按地点分组的树形 UI。
- 位置查询从「一棵树」变成「一片森林」；RPC 增加根列表。
- 未来若需要跨地点转移流程，仍由 `inventory` 拥有，不复制到 `locations`。

**备选**：单根 + 虚拟顶层（否决，所有地点被迫同树，语义不自然）；每个地点一个家庭（否决，v1 单家庭）。

---

## D25 · 证件模块 v1 只存掩码

**状态：已定**

**背景**：身份证、护照、银行卡属于高敏感数据；v1 的 DB 文件不加密，Web 路径又经行星明文。

**选择**：

- `identity` 只存掩码、后四位、颁发方、有效期、状态等结构化字段。
- 不存完整证件号/银行卡号、CVV、PIN、磁道/芯片数据。
- 完整信息看扫描件；扫描件归 `documents`，按最高敏感级别保护。
- 查看/下载扫描件写审计；Web 默认脱敏，高敏感操作建议原生。
- 如未来需要完整号码，先增加宿主加密字段能力，再迁移。

**后果**：

- 模块可直接在 v1 落地，不依赖 SQLCipher 或字段加密。
- 用户无法在结构化字段中复制完整号码，需要打开扫描件。
- 导出仍是高敏感操作；备份按最高敏感级别处理。

**备选**：完整号码明文入库（否决）；用 `ModuleConfig` 存 JSON（否决，不可查询、难审计）；v1 上 SQLCipher（后续评估）。

---

## D26 · 证件水印分享按需生成

**状态：已定**

**背景**：证件扫描件外发时需要标明用途和接收方，降低被挪用的风险；不能修改原件，也不应让水印副本长期堆积。

**选择**：

- 水印由 `documents` 统一生成；`identity` 只提供入口、校验记录与扫描件关联，并传上下文。
- 原始文件永远不修改；水印副本默认按需生成、流式返回，不落盘。
- `recipient` 与 `purpose` 必填；水印含接收方、用途、日期、`shareId`。
- 图片纠正 EXIF 方向、叠加后重新编码并剥离元数据；PDF 逐页栅格化后输出扁平化 PDF；拒绝加密 PDF。
- 每次生成新 `shareId`，审计操作者、文档、上下文、接收方、用途、时间、页数。
- 水印是威慑与追溯，不是 DRM；不能阻止截图、裁剪或恶意去除。

**后果**：

- 分享流程不产生新的文档记录，不需要额外的文件 GC。
- 水印生成有 CPU 成本，需要限流、大小/页数限制与超时。
- 需要 PDF 渲染库与中文字体；实现前先做字体与性能验证。
- 如需「我发过给谁」与撤销，后续增加分享记录表，不改变本决策的生成方式。

**备选**：修改原图（否决）；持久化水印副本（暂缓，需派生文件与 GC）；PDF 注释叠加（否决，容易被移除）。

## D27 · 日历与任务分离

**状态：已定**

**背景**：日历和待办都关心日期，但语义不同。把纪念日当任务会让「完成」变得别扭；把家务塞进事件又缺少分派与完成记录。

**选择**：

- `calendar` 拥有事件、纪念日、生日、多日活动与参与者。
- `tasks` 拥有待办、周期、分派、完成记录。
- 日历 UI 只读叠加 `tasks` 的到期项；点击跳转任务详情，不在日历改状态或改期。
- 生日/纪念日 v1 由 `calendar` 建事件，避免和 `members` 双份维护。
- 重复事件服务端展开；v1 不支持单次例外/完整 RRULE；日期不存在时跳过。

**后果**：

- 同一天需要聚合两个 RPC，但所有权清晰。
- 提醒仍需统一通知能力或由 `tasks` 生成，`calendar` 不内置调度。
- 未来若要拖拽改期任务，需要显式调用 `tasks`，不能本地改。

**备选**：日历与任务合并（否决，完成语义冲突）；日历只做展示不存事件（否决，无法管理纪念日）；把生日放 `members`（否决，重复维护）。

---

## D28 · 饮食与库存、任务分离

**状态：已定**

**背景**：菜谱、菜单、采购清单、库存和家务都围绕「吃」，但所有权不同；混在一起会让库存与任务状态难以保持一致。

**选择**：

- `meals` 拥有菜谱、食材、菜单计划、采购清单。
- `inventory` 拥有库存与出入库；`meals` 只引用 `inventory_item_id`，不自动扣减。
- `tasks` 拥有买菜/做饭等任务；`meals` 不复制任务状态。
- `calendar` 可以只读展示当天菜单，但餐次仍归 `meals`。
- 采购清单勾选只表示「已买」，不代表「已入库」。

**后果**：

- 需要显式的库存调整动作，不能靠勾选采购清单自动入库。
- 菜谱食材允许自由文本，降低对库存主数据的依赖。
- 菜单与任务可以在 UI 聚合，但写操作各回各家。

**备选**：库存内置采购清单（否决，菜谱/菜单会反过来依赖库存）；任务内置菜单（否决，完成语义冲突）；自动扣库存（暂缓，容易与实际消耗不符）。

## D29 · 健康记录隐私优先

**状态：已定**

**背景**：健康数据比普通家庭数据敏感；预约、用药提醒、报告文件与健康记录本身分别属于不同模块。

**选择**：

- `health` 只拥有人类健康记录；宠物健康归 `pets`。
- 记录默认 `private`（本人 + `health.admin`）；用户显式改为 `family` 才对家庭成员可见。
- 普通成员只能写自己的记录；代写他人需要 `health.admin`。
- 预约归 `calendar`，提醒归 `tasks`，报告/处方归 `documents`。
- Web 默认只显示摘要；附件下载、导出、详细内容优先原生。
- 健康正文/附件不写日志；v1 依赖磁盘加密，后续再评估字段加密。

**后果**：

- 健康模块需要记录级可见性过滤，不能只靠模块权限。
- 家庭共享需要用户主动选择，默认不透明。
- 导出与附件下载按高敏操作处理，可能要求重新认证。
- 未来若要支持未成年人/成人隐私，需要更细的 ACL 或管理员破窗流程。

**备选**：默认家庭可见（否决，隐私风险）；宠物健康并入 `health`（否决，字段与生命周期差异大）；预约/提醒复制到健康模块（否决，状态会漂移）。

## D30 · 宠物与植物共用档案，护理归任务

**状态：已定**

**背景**：猫狗鸟鱼虫和植物都需要档案与护理记录，但物种差异大；护理又天然是周期任务，容易和 `tasks` 重复。

**选择**：

- `pets` 用一个模块覆盖猫、狗、鸟、鱼、昆虫、植物与其他。
- `kind` 只决定默认 UI 与护理类型，不限制可记录内容。
- 档案、成员关联、护理日志由 `pets` 拥有；护理日志只追加。
- 周期护理计划/提醒归 `tasks`，用 `subject_type="pets.pet"` 指向宠物。
- 食物、药品、耗材库存归 `inventory`；`pets` 不自动扣减。
- 照片、疫苗本、宠物病历归 `documents`。
- 宠物医疗不混入人类 `health`；去世/送养保留历史。

**后果**：

- 需要按 `kind` 做不同的 UI 默认值，但数据模型保持统一。
- 护理提醒不在宠物模块内，避免两套周期引擎。
- 物种专属指标（水温、pH、光照、体重）先放 `metadata_json` 或备注。
- 未来若差异过大，再拆 `plants` 或宠物医疗子模块。

**备选**：猫狗与植物拆两个模块（暂缓，档案结构足够接近）；护理计划内置 `pets`（否决，重复 `tasks`）；宠物健康并入 `health`（否决，权限与生命周期不同）。

## D31 · 智能家居按 Profile / Capability / Driver 三层解耦

**状态：已定**

**背景**：智能家居的设备类型、操作和协议都会持续增加；如果每个设备写一个类、每个动作加一个 RPC、每个协议加一个 enum，核心和 UI 很快会被厂商分支淹没。

**选择**：

- 设备类型是数据化的 `DeviceProfile`，由 `Capability` 组合而成，不写设备类。
- 操作归 `Capability` 的命令与 schema；统一走 `smart_home.commands.execute`，不按设备/动作新增 RPC。
- 协议是 `ProtocolDriver` 模块；核心只依赖 SPI，不出现厂商字段、协议 enum 或 SDK 调用。
- 驱动支持点对点与网关型；统一用 `AdapterInstance` + `DeviceBinding` 表达。
- 状态带 `reported / inferred / optimistic`；命令结果不等于真实状态。
- 新增设备类型优先加 Profile；新增协议装驱动；新增通用能力才改核心。
- 红外码、设备型号、按钮布局是数据；协议实现是代码。
- 核心表、RPC、Capability、Profile ID 不写死厂商或型号；具体设备/型号只出现在驱动配置或 Profile 数据中。
- 门锁 v1 只读，不注册 `unlock`；蓝牙音频由独立音频服务处理。
- 驱动是受信任 `.hmod`，安装时展示发布者与网络/蓝牙/串口需求；高风险命令由策略层拦截。

**后果**：

- 核心代码不随厂商设备增长；新增设备类型和协议可独立交付。
- 需要维护 Profile/Capability 注册表、schema 版本与驱动契约测试。
- 数据化只适合码表、设备组合与 UI 提示；复杂协议仍需写驱动。
- 自动化必须引用稳定的 Capability，不能引用厂商方法。
- 多绑定与状态融合会增加复杂度；v1 只启用主绑定。

**备选**：每个设备一个 Kotlin 类（否决，厂商分支失控）；每个动作一个 RPC（否决，RPC 爆炸）；协议 enum + `when`（否决，新增协议改核心）；所有协议用通用 DSL（否决，复杂协议不可行）；把门锁控制直接接进自动化（否决，安全风险）。

## D32 · 实际做饭记录与菜谱、菜单分离

**状态：已定**

**背景**：菜谱是模板，菜单是计划，实际做饭是已经发生的事实。用户做完饭会拍照，需要低摩擦记录；把照片塞进菜谱会丢失「哪一天、哪一顿、做得怎么样」的信息。

**选择**：

- `meals` 增加 `CookLog` / `CookLogDish`，记录实际做饭时间、菜品、份数、评分、备注。
- 菜谱、菜单计划、做饭记录三者分离；记录可从菜谱/菜单预填，但不自动回写。
- 一条记录可包含多道菜；菜品名称做快照，菜谱归档后仍可显示。
- 做饭照片归 `documents`，关联 `targetType="meals.cook_log"`、角色 `cook_result`。
- 不自动扣库存、不自动完成任务；需要时由 UI 显式调用对应模块。
- 做饭记录不自动写入日历；日历只读展示菜单计划。
- 评分可选 1–5；v1 不做推荐算法。

**后果**：

- 用户可以不建菜谱、不排菜单，直接记录一顿饭。
- 照片与记录是跨模块流程；先建记录再上传，失败可重试。
- 需要维护菜谱「做过 N 次」聚合与历史快照。
- 库存与任务状态不会因记录而漂移。

**备选**：把记录塞进菜谱（否决，失去时间线）；把记录当菜单计划（否决，计划与实际混淆）；新建独立模块（暂缓，边界仍属于饮食）；自动扣库存/完成任务（否决，容易与实际不符）。

## D33 · 条码是物品标识，扫码在客户端完成，外部查询按需

**状态：已定**

**背景**：商品条码能把「建物品 + 入库」压缩成扫一下；但条码本身只标识商品，不标识批次，而且外部商品库查询会把家庭购买行为发到第三方。把解码、查询和写入混在一起，容易造成隐私泄露和重复物品。

**选择**：

- 条码归 `inventory`，用 `ItemBarcode` 建立「条码 ↔ 物品」映射；批次、数量、保质期仍归 `StockLot`。
- 解码在卫星/浏览器完成；恒星只接收条码字符串并在服务端校验/归一化，不接收相机帧、不存条码图片。
- GTIN 家族（EAN/UPC/GTIN-14）验证校验位并统一为 14 位；其他码按不透明字符串保存。
- 一个活跃条码只指向一个物品；一个物品可有多条码；归档映射保留，扫到后提示恢复，不静默改绑。
- 外部商品库查询是可选 Provider，必须显式触发；结果只作草稿，用户确认后才写入，不自动建物品。
- 外部图片不下载、不热链；用户自己的照片归 `documents`。
- 二维码不解析 URL、不自动执行动作；扫码枪输入按不可信文本校验。
- 不建全局商品目录；条码映射只在当前家庭内有效。

**后果**：

- 离线也能扫码建物品、入库；外部查询失败不阻塞主流程。
- 需要维护 Provider 配置、限流、缓存 TTL 与冲突处理。
- 同一商品多包装需要多条码；称重商品的内嵌价格码暂不解析。
- 隐私边界清晰：相机数据不出设备，外发只发生在用户点按查询时。

**备选**：新建 `catalog` 模块（暂缓，边界仍属于物品）；服务端解码（否决，上传图像与隐私成本高）；扫码即自动建物品/入库（否决，误识别会污染库存）；硬编码单一外部商品库（否决，无法替换且泄露面大）；把条码存进 `Item` 单字段（否决，无法支持多包装与归档历史）。

## D34 · 价格历史按观测追加，单位价格归一化

**状态：已定（实施延后）**

**背景**：`StockLot.price_cents` 只能表示一次入库的价格，无法表达货架价、促销、不同包装和不同商家；直接拿批次价画图会把「总价」和「单价」混在一起，也无法比较 500g 与 1kg。

**选择**：

- `inventory` 增加 `PriceObservation` 与 `Merchant`；价格按观测追加，不静默改历史。
- 入库可选带价格，`stock.adjust` 在同一事务写库存流水与 `kind=purchase` 观测。
- 观测存总价、数量、每包装净含量与基础单位；单位价格由 `total_price_cents / (quantity × net_amount)` 归一化。
- 只比较相同币种与相同基础单位；不做汇率换算，不混合 g/ml/piece。
- 作废用 `voided_at`，纠正用新记录 + `supersedes_id`；不物理删除。
- 统计与图表按需计算：最新、最低、最高、平均、涨跌幅；按日/周/月分桶，不插值，促销可标记。
- 图表只读；原生用 Compose Canvas，Web 用 SVG；不引入第三方图表库。
- 价格来源先支持手动、货架/网价与入库；小票导入后续再做，不做自动抓价、预测、提醒与预算。
- 商家是家庭内主数据，不写死品牌；线下门店只引用 `location_id`。

**后果**：

- 价格与库存数量解耦，货架价不会影响库存。
- 需要维护单位换算、币种筛选、作废/纠正与图表桶聚合。
- 观测会持续增长；靠索引与分桶控制查询成本，不做物化聚合。
- 同一商品多包装、多商家可比较，但称重/计件之间仍不可直接比较。
- 未来若扩展到预算、比价、提醒，再评估拆独立模块。

**备选**：只从 `StockLot` 画图（否决，缺货架价且单位不清）；存聚合结果（否决，易漂移）；自动抓价（否决，合规与稳定性差）；跨币种自动换算（暂缓）；新建 `prices` 模块（暂缓，当前边界仍在物品）；静默改价（否决，历史不可信）。

## D35 · 家庭沟通归 `messages`，私聊最小可见，公告走主页横幅

**状态：已定**

**背景**：家庭既需要「所有人都能看到」的通知，也需要两人私聊；聊天记录要能回看。把聊天塞进 `tasks`/`calendar` 会与完成、提醒语义冲突；用外部 IM 则历史、成员和权限都散落在家庭数据之外。主页公告还需要一个统一的发布与展示入口。

**选择**：

- 新增 `messages` 模块，拥有公屏、两人私聊、消息、已读位置、主页公告与公告关闭记录。
- 每个家庭一个 `public` 会话；私聊按两位成员排序生成唯一 `direct_key`；不能和自己私聊。
- 消息用会话内单调 `seq` 排序与分页；发送带 `client_id`，重试幂等；不做离线发件箱。
- 私聊只有两位参与者可见，管理员没有读取入口；公屏管理员可撤回，私聊只有发送者可撤回。
- 消息不改历史；撤回清空正文并保留「已撤回」占位；`sender_name` 发送时快照。
- 已读只存每成员 `last_seq`，不提供逐条已读回执。
- 公告由管理员发布，支持生效/结束时间、`info/warning/critical` 级别、是否可关闭；`critical` 强制不可关闭；主页过滤已关闭项后只展示第一条，按级别排序，关闭按成员记录。
- 公告归 `messages`，不复制成日历事件或任务；不做强制确认与定向。
- Web 只提供公屏与公告，私聊仅原生，避免行星看到 Web 明文；Web 服务端直接拒绝私聊会话的列表、读取与发送；原生私聊走宿主端到端传输，不是消息级端到端加密。
- 消息正文不进日志、审计与通知预览；恒星数据库存明文，隐私边界是应用层。
- v1 只发文本；附件/图片后续走 `documents`，搜索、导出、保留期后续再做。

**后果**：

- 家庭沟通与成员、权限、备份在同一套数据里，历史可回看。
- 私聊隐私依赖应用层与操作权限，不是数据库加密；DB 管理员/备份仍可见。
- Web 体验不完整：只能看公屏和公告，私聊必须用原生。
- 需要维护 `seq` 分配、幂等、未读与公告时间窗。
- 未来若要端到端私聊，需要新的密钥与多设备同步方案，不能只加字段。

**备选**：用外部 IM（否决，历史与成员权限不可控）；公告塞进 `calendar`/`tasks`（否决，完成与重复语义冲突）；聊天与公告拆两个模块（暂缓，边界仍围绕家庭沟通）；管理员可读私聊（否决，破坏最小可见）；v1 就做端到端加密（暂缓，复杂度高）；v1 支持图片/文件（暂缓，先走文本与文档模块）。

## D36 · 旅行计划与记录共用 Trip，日历只读叠加

**状态：已定**

**背景**：旅行既有「出发前计划」，也有「回来后记录」。如果拆成 `TripPlan` 与 `TripRecord` 两张主表，同一趟旅行会出现两个身份，日期、同行人、目的地容易各改各的；如果把行程直接建成日历事件，计划变更会与日历副本漂移。旅行日期与住宿地址还会暴露家中无人，需要明确的可见性边界。

**选择**：

- 新增 `travel` 模块，拥有旅行、目的地、同行人、逐日行程、清单与游记。
- 一趟真实旅行只有一条 `Trip`；计划阶段用逐日行程/清单，记录阶段用游记与实际完成状态；补记已完成旅行可直接建 `completed`，不要求先有计划。
- `Trip` 状态为 `planning` / `confirmed` / `completed` / `cancelled`；「进行中」按日期派生，不自动写状态。
- 日期用目的地当地日期，时间用当地墙上时间；v1 不做跨时区自动换算。
- 日历不复制旅行；原生日历只读叠加 `travel.trips.listInRange`，点击跳转旅行详情；Web 日历不显示旅行。
- 准备任务归 `tasks`，用 `subject_type="travel.trip"` 关联；旅行不复制任务状态。
- 票据、保险单、游记照片归 `documents`；证件号码归 `identity`；旅行只保存逻辑引用。
- 同行人可以是成员或仅记录姓名；成员移除后历史仍显示快照名。
- v1 不做机票/酒店/门票预订、地图导航、旅行记账、票据 OCR、天气/航班抓取、公开分享与离线同步。
- 旅行默认仅家庭成员可见，`guest` 无权限；通知、日志与审计不记录具体地址与游记正文。
- v1 不提供 Web 旅行页；行程、住址与游记只在原生客户端。

**后果**：

- 计划与记录共享同一身份，避免重复与漂移；但 `Trip` 同时承载两种阶段，UI 需要清楚区分「行程」与「游记」。
- 日历只读叠加需要客户端并行调用 `travel` 与 `tasks`；日历不承担旅行编辑。
- 旅行准备任务与打包清单是两套东西：任务有历史和提醒，清单只保留勾选状态。
- 不做花费流水意味着无法回答「这次旅行花了多少」；预算只是计划值。
- 原生优先保证隐私，但 Web 用户无法查看行程；后续若开放 Web，需要单独的只读与脱敏策略。
- 同行人非成员只能被记录，不能登录查看；后续若需要共享，需新增邀请与权限模型。

**备选**：`TripPlan` + `TripRecord` 两张主表（否决，身份重复且易漂移）；把行程建成日历事件（否决，计划变更会与日历副本冲突）；用 `tasks` 当行程（否决，任务语义是完成/提醒，不是时间线）；用外部旅行 App（否决，历史与家庭数据不可控）；内置预订/地图（否决，范围与合规成本过高）；旅行记账（暂缓，等财务模块）；Web 行程页（暂缓，先保隐私）；离线地图（暂缓，v1 在线优先）。

## D37 · 运动记录独立于健康档案，默认私密且统计只读

**状态：已定**

**背景**：运动记录既有结构化的时长、距离、步数，也有心率、RPE、备注等能推断作息与身体状况的字段；健康档案记录的是就诊、用药、过敏等医疗事件。如果把运动塞进 `health.record.metadata_json`，统计口径会变得脆弱，隐私边界也会和医疗记录混在一起。另一方面，运动统计需要稳定的「活跃天数、连续天数、按类型分布、个人最佳、目标进度」定义，聚合结果还可能把私有记录泄露给家庭成员。

**选择**：

- 新增 `fitness` 模块，拥有运动类型、运动记录、目标与统计口径。
- v1 只做「一次运动」级别的记录：类型、开始时间、本地日期、时长，可选距离/步数/热量/平均心率/最大心率/RPE/备注。
- 运动类型数据驱动：内置通用类型（走路、跑步、骑行、游泳、徒步、瑜伽、力量训练、球类、其他），管理员可扩展；核心不写厂商、设备型号或品牌。
- 运动默认 `private`，逐条显式改为 `family`；管理员没有读取私有记录的入口，也没有破窗。
- 统计只基于请求者可见的记录；查看他人统计时只汇总其 `family` 记录，UI 明确标注「仅统计家庭可见记录」。
- 统计按成员本地日期 `local_date` 分桶，缺失桶补 0，不做插值/平滑/预测，最多 500 个桶。
- 当前连续天数从 `to` 当天向前数；`to` 当天没有运动时允许从 `to - 1` 天开始；`to` 与 `to - 1` 都没有运动则为 0。
- 个人最佳按运动类型的 `primary_metric` 计算；并列取更早记录。个人最佳不是 `achievements` 记录。
- 目标是本人私有的周期目标（日/周/月/年），按可见记录计算进度；超过 100% 保留真实数值，UI 进度条封顶。
- 提醒与计划归 `tasks`；运动不自动完成任务，任务也不自动生成运动记录。损伤/不适归 `health`，运动模块不做诊断。
- v1 不提供 Web 页面，Web 网关拒绝 `fitness.*` RPC；不提供日历叠加。
- v1 不做 GPS/轨迹、穿戴设备/HealthKit/Google Fit/Strava、组数/次数/重量、训练计划、社交排行、挑战赛、公开分享、自动热量估算、医疗解读与离线同步。

**后果**：

- 手动录入是主要摩擦点；没有穿戴同步，用户需要自己填时长与距离。
- 隐私边界清晰，但家庭统计会因私有记录而偏低；管理员也无法处理私有内容，需要本人自行修改。
- 统计读时计算，数据量增大后查询成本上升；v1 依赖 `(member_id, local_date)` 索引与 500 桶上限，后续再评估按日 rollup。
- 不记录 GPS 与力量组数，无法替代专业训练 App；换来的是一致、可解释、隐私优先的家庭统计。
- 仅原生意味着 Web 用户无法查看运动；后续若开放，需要单独的脱敏与只读策略。
- `local_date` 依赖客户端传递，服务端只能做 ±1 天校验；跨时区旅行时以用户填写的本地日期为准。

**备选**：把运动放进 `health.record` 的 `metadata_json`（否决，统计口径脆弱且隐私语义混淆）；用 `tasks` 当运动记录（否决，任务语义是完成/提醒，不是统计事实）；拆独立 `workouts` 模块（否决，命名过窄，目标与统计同属运动域）；用外部运动 App（否决，家庭数据与隐私不可控）；v1 就做家庭排行榜（否决，放大隐私与公平性问题）；v1 接穿戴设备（暂缓，权限与平台成本高）；v1 做 GPS 轨迹（暂缓，敏感度与实现成本高）；v1 做组数/次数（暂缓，先做会话级）；v1 提供 Web 页（暂缓，先保隐私）；v1 建统计汇总表（暂缓，先保证口径一致）。

## D38 · DIY 改装只走本地驱动，ERP 不承担硬件安全

**状态：已定**

**背景**：用户可能想自己改装热水壶、洗衣机等设备，把电路或控制面板接入家庭 ERP。现有 `smart_home` 已经用 `DeviceProfile` + `Capability` + `ProtocolDriver` 支持数据驱动扩展，但主电源、加热、进水与高速旋转的安全不能靠软件保证；远程开关和自动化还可能把「命令已发送」误当成「设备已安全执行」。需要明确 DIY 设备的接入边界、风险分级与本地驱动方式。

**选择**：

- DIY/自制设备通过本地 `ProtocolDriver` 接入（如本地 MQTT、ESPHome、Modbus 网关、BLE 网关），走 `AdapterInstance` + `DeviceBinding`；不做公网端口映射，不默认接厂商云。
- 接入优先级：外部非侵入式监测（智能插座、钳形 CT、温度/振动/漏水/门磁）＞ 认证智能插座控制整机电源 ＞ 低电压面板信号接入 ＞ 主电源/内部电路改装。
- 主电源/内部电路改装只由持证电工按当地规范完成；ERP 不作为漏电、干烧、过热、漏水、门锁失效的安全联锁，也不承诺改装合规与保修。
- 新增通用能力：`power_meter`、`temperature`、`water_level`、`cycle_state`、`remaining_time`、`door_state`、`leak`、`vibration`、`fault_code`；高风险命令能力单独用 `heater_power`、`appliance_power`、`cycle_control`，不把加热负载塞进低风险 `power`。
- `heater_power` 为 `critical`，`appliance_power` / `cycle_control` 为 `high`；三者要求 `localOnly=true`、`requiresReauth=true`、原生客户端、逐次手动确认；Web 与自动化默认拒绝。
- 热水壶开启必须校验水位/温度/最长加热时间，并在无电流、超时或离线时默认断开；没有水位联锁时不开放远程/自动加热。
- 洗衣机启动必须校验门关闭（若可读锁定状态，运行中必须锁定）、漏水、故障码与 `cycle_state=idle`；运行中不通过断电控制；没有门锁/漏水传感器时不开放远程启动。
- 状态区分 `reported` / `inferred` / `optimistic`；功率曲线推断的 `cycle_state` 标记 `inferred`，命令结果不等于真实状态。
- v1 只保留最后值与事件，不保留连续功率曲线；后续若增加历史曲线，必须降采样，不用功率曲线长期推断家庭作息。
- v1 先复用内置 Profile；用户自定义 Profile/Capability 仍待定，DIY 设备不因为「能发现」就自动受管。

**后果**：

- 安全边界清晰，但 v1 更像「监测 + 提醒 + 低风险控制」，不是完整的远程家电控制。
- 热水壶、洗衣机默认不能远程启动；需要用户在场、本地网络、重新认证与传感器联锁。
- 用户需要认证硬件与持证电工，DIY 成本上升；但能保留原机保护、保修与保险有效性。
- 本地驱动需要维护发现、配对、超时、重连、熔断、事件去重与契约测试；没有云托管的便利。
- 高风险能力单独建模会增加 Capability 数量；后续可评估 Profile 级 `riskOverrides`，但不能削弱默认策略。
- 不接云端、不做 OTA，减少攻击面，但固件升级与设备诊断需要用户自行完成。

**备选**：允许 DIY 设备直连厂商云（否决，隐私与可用性不可控）；用软件定时器/继电器替代硬件安全联锁（否决，失效后果不可接受）；开放 `rawCommand` 给 UI/自动化（否决，绕过 schema 与策略）；v1 支持主电源改装（否决，安全与合规责任不清）；v1 开放用户自定义 Profile（暂缓，先固化内置 Profile 与风险模型）；ERP 触发固件 OTA（暂缓，先只报告版本）；用功率曲线做家庭作息推断（否决，隐私风险高）。

## D39 · 星群是恒星的薄 I/O 末梢，不承担业务与安全

**状态：已定**

**背景**：恒星是一台笔记本，但要覆盖全屋的采集与控制。若每个房间放一台小电脑，会出现多份数据库、多套权限与同步冲突；若把每个按键和传感器都拉线回笔记本，长线干扰、地环路误触发与施工成本都不可控。需要明确分布式节点的命名、职责边界与接入方式。

**选择**：

- 命名：**星群（Cluster）** 指恒星直接管辖的固定 I/O 节点集合，单个节点叫 **星节点（Room Node）**。恒星、行星、卫星是 ERP 协议栈角色；星群不是协议角色，只在部署 `smart_home` 房间节点时存在。
- 术语说明：星群借天文 asterism（星群）的意象，不是 `star cluster`（中文是「星团」）；英文与代码仍用计算术语 `cluster` / `node`，文档不写「星群 = star cluster」。
- 星节点只做采集、消抖、执行、本地兜底、事件缓存与健康上报；不做业务逻辑、不写业务库、不接公网、不接摄像头与麦克风。
- 恒星是唯一大脑：broker、驱动、策略、自动化与持久化都在恒星；节点主动连恒星，不做入站端口映射。
- 通信只用本地 MQTT，主题 `home/<node>/...`；`availability` 与 `state` retain，命令与事件不 retain，靠 `seq` 与 `idempotencyKey` 去重。
- 映射：一个星节点 = 一个 `AdapterInstance`（`driverId=mqtt.local`）；端点 = `DeviceBinding.nativeId = <nodeId>/<endpoint>`；能力复用 Capability，不新增协议字段。
- 离线：节点环形缓存事件，满了丢最旧并上报 `dropped`；`availability=offline` 时能力置 `unknown`，不显示「已关闭」。
- 本地兜底：物理开关直接控制负载；断网时节点只跑固定本地规则，不下发用户脚本。
- 硬件：默认 ESP32-C3/S3；固定位置优先以太网或 PoE；Pico W 用于极简节点；Arduino Nano 只作 I/O 扩展，不作网络节点；电池传感器经网关接入，不计入星群。
- 长线按键：节点放床边，按键线 1–2 m；不把长线拉回恒星。
- 安全：每节点独立凭据 + 前缀 ACL；新节点需原生端确认；节点凭据不是用户身份；v1 不做 OTA；节点不作为安全联锁（见 D38）。

**后果**：

- 多出一批需要供电、配网与固件版本管理的设备，运维成本高于一体机方案。
- 恒星仍是单点；笔记本休眠、系统更新或误关机都会影响全屋，必须按常开服务器对待，并接受降级运行。
- 节点没有本地业务逻辑，断网时只能执行固定规则，跨房间联动失效。
- 事件顺序以 ERP 的 `received_at` 为准，节点时钟不可信；离线补传存在丢失窗口，需要 UI 明示。
- 局域网内 MQTT 默认明文，靠 VLAN/独立 SSID 与独立凭据隔离，TLS 可选而非强制。
- 「星群」与天文的 `star cluster`（星团）不是同一概念，文档与沟通中需要解释一次，避免误译。

**备选**：每个房间一台小电脑（否决，多份数据与权限，权威分裂）；所有线缆拉回恒星（否决，长线干扰与施工成本）；节点跑业务逻辑或本地数据库（否决，违背恒星唯一权威）；节点直连 HTTP 不用 broker（否决，缺 LWT、重试与背压）；自建 Zigbee/Thread 协议栈（否决，成本远高于收益）；v1 做节点 OTA（暂缓，先保证可运维的最小闭环）；节点承担安全联锁（否决，见 D38）。

## D40 · 衣物归 `wardrobe`，抽卡只抽已存搭配，天气可降级

**状态：已定**

**背景**：用户希望管理衣物、记录洗烘注意、按天气抽一套搭配。`inventory` 是数量型库存，装不下「单件、有洗护要求、有穿着历史」的语义；`smart_home` 只拥有洗衣机设备，不知道柜子里有什么。而穿搭推荐如果交给规则从单件组合，会产出不可解释也不好看的结果；天气又必须引入外部数据，与本地优先冲突。

**选择**：

- 新增 `wardrobe` 模块，拥有衣物、洗护画像、搭配、穿着记录、洗涤批次与天气快照。
- 单件可追踪的衣物归 `wardrobe`；成打/未拆封的消耗品归 `inventory`；衣物尺码是衣物属性，身体尺寸归 `members`。
- 洗护用 ISO 3758 对应的枚举（水温上限、漂白、烘干、熨烫、干洗），不用自由文本。
- 「气候」不存粗糙气候带标签，改用搭配的 `comfort_min_c` / `comfort_max_c` 体感温区加 `seasons`，更精确也更少依赖。
- 抽卡只从用户自己保存的搭配里抽，不程序化组合单件；理由：组合需要审美判断，规则化会产出荒谬搭配。
- 同一成员同一天首次抽卡按 `hash(memberId, localDate)` 播种，刷新结果稳定；每天最多 3 次，重抽排除刚抽到的。
- 候选集先过滤：未归档、衣物全部可穿（排除 `dirty`/`washing`/`drying`/`ironing`/`repair`/`lent`/`discarded`）、季节匹配、温区覆盖今日体感温度、降水与大风约束、场合匹配。
- 权重含近期惩罚（7 天内抽中 ×0.2、穿过 ×0.4）与久未抽到奖励（30 天 ×1.5），连续 5 次未出现的搭配 ×3 保底。
- 天气走 `WeatherProvider` SPI：默认手动填写，可显式开启城市级 HTTP 预报；失败用最近快照并标 `stale`，抽卡降级为按季节筛，不阻塞。
- 天气只用城市/区级粗位置，不存 GPS 与家庭精确地址；快照只保留 14 天。
- 洗护冲突检查是确定性规则，输出 `ok` / `warn` / `conflict` 与逐条原因；只警告，不改洗衣机程序（承接 D38）。
- 洗衣机 `cycle_state=done` 只触发提醒，不自动把衣物标为 `clean`。
- 衣物与搭配默认家庭成员可见（便于代洗、代收拾）；穿着记录与抽卡记录默认仅本人可见，管理员无读取入口。
- v1 不提供 Web 衣物页面，服务端拒绝 Web 来源的 `wardrobe.*` RPC。

**后果**：

- 抽卡不会创造新搭配；用户不主动存搭配时功能空转，需要先建几套。
- 天气依赖外部源或手工输入；不填也能用，但推荐精度下降。
- ISO 3758 枚举需要用户理解符号，UI 必须配图标与文案，不能只给代码。
- 冲突检查只基于用户录入的画像；新衣物不录就没有保护。
- 衣物家庭可见意味着成员能看到彼此的衣橱，隐私边界转移到穿着记录而非衣物本身。
- 多出一套表和 RPC，但避免了 `inventory` 长出衣物专用字段。

**备选**：把衣物并入 `inventory`（否决，数量与个体语义冲突）；并入 `health`（否决，洗护与医疗无关）；从单件随机组合成搭配（否决，审美不可规则化）；用大模型生成搭配（暂缓，解释性、隐私与成本都不合适）；天气强制接云（否决，违背本地优先）；完全不存天气只按季节（部分采纳，作为降级路径）；衣物默认私密（否决，家庭成员需要知道柜子里有什么以便代洗）。

**变更**：D41 用「单件保暖分级」重做了组合逻辑，本决策中「抽卡只从用户自己保存的搭配里抽，不程序化组合单件」的条款已被 D41 取代；其余条款仍然有效。

## D41 · 单件保暖分级让系统可以自由组合搭配

**状态：已定（部分取代 D40 的抽卡来源条款）**

**背景**：D40 只允许抽用户存好的整套搭配，理由是程序化组合会产出「羽绒服 + 短裤」。但这意味着用户必须先手工维护几套，功能才用得上；而「羽绒 + 短裤」的根因不是随机组合本身，而是缺少「这件衣服适合多少度」这个字段。补上它，组合就能变成确定性计算，而不是审美判断。

**选择**：

- 每件衣物增加 `warmth`（1–5）、`slot`、`layer`、`visible`、`rain_ok`、`wind_ok`；用户只选档位，不填温度。
- 系统内置一张「保暖等级 → 适穿体感温度」表：1 ≥24 °C、2 20–29 °C、3 14–24 °C、4 3–19 °C、5 ≤10 °C；允许 ±2 °C 宽容，可按「怕冷/怕热」整体平移，单件可用 `temp_override_*` 覆盖。
- 合法性判定改成「今日体感温度是否落在该件衣物的适穿区间内」，不再比较上下身保暖差。
- 因为羽绒 ≤10 °C、短裤 ≥24 °C，两个区间不相交，「羽绒 + 短裤」在模型层面不可能出现；不需要为它写特例。
- 槽位：`upper`、`lower`、`feet`、`head`、`accessory`；层：`base`、`mid`、`outer`、`single`。
- 不可见内搭允许比当日区间低 1 级，避免误杀「羽绒 + 短袖内搭」这类真实穿法；外露层不允许下探。
- 新增 `wardrobe.outfits.compose` 从单件组合；保留 `wardrobe.outfits.draw` 抽整套。两者共用权重、冷却与保底。
- 组合约束：上身最多 3 层、每层 1 件；候选乘积超过 5,000 时改加权采样。
- 内搭分两类：功能内搭按「保暖档 + 干净件数」批量管理（`BaseLayerStock`），不逐件、不写穿着记录、不参与风格；造型内搭按件录入，`visible=1` 才参与场合与风格。
- 组合结果可存为搭配，之后走整套模式。

**后果**：

- 每件衣物多两个必填字段（`slot`、`warmth`），录入成本上升；需要「按类别给默认值」来降低摩擦。
- 温度带是经验值，南北差异与个人差异靠整体平移和单件覆盖解决，仍会出现「系统觉得合适但我觉得冷」。
- 功能内搭只有件数、没有个体，无法追溯具体哪件，也无法做单件洗护冲突。
- 组合质量取决于录入完整度；缺下装或鞋时会频繁返回「无候选」，需要清楚的缺失提示。
- 多了一套组合算法与组合空间保护，复杂度高于「只抽整套」。

**备选**：只抽整套搭配（否决为唯一模式，用户必须先手工建套）；比较上下身保暖差（否决，阈值难调，还会误判三层穿法）；每件直接填温度区间（否决，录入成本高且用户不知道填多少）；用大模型判断搭不搭（否决，不可解释、隐私与成本不合适）；内搭一律逐件管理（否决，功能内搭每天换，逐件记录会产生大量噪声）。

## D42 · 开封期限归库存，剩菜归饮食

**状态：已定**

**背景**：开封后的牛奶、酱料和吃剩的一盒菜看起来都是「快过期的东西」，但前者是包装商品，有批次、条码、价格、位置与补货；后者是烹饪产物，有菜谱、做饭记录和口味。把剩菜建成库存批次，会制造没有条码、没有价格的假物品，污染补货与价格统计；把开封日期塞进 `meals`，又会让库存的临期视图漏掉一半。

**选择**：

- `StockLot.opened_at` / `use_within_days` 归 `inventory`；有效期限取 `min(expires_at, opened_at + use_within_days)`，只用于查询与事件。
- 开封是批次级动作。一包多件先 `inventory.lots.split` 再 `open`，不复制物品、不改条码。
- 熟食剩菜用 `meals.Leftover`，引用 `cook_log_id`，记录 `stored_at`、`location_id`、`eat_by` 与状态；不创建 `Item`，不进库存流水。
- 两者都不自动扣减、不自动丢弃；吃掉或扔掉由用户确认，丢弃写原因。
- 临期视图可以合并展示，但写操作各自回到拥有者。

**后果**：

- 库存与饮食的边界变清楚：一个管「包装还剩多少」，一个管「这顿剩了什么」。
- 需要维护两套期限计算与两个列表，UI 要合并展示。
- 开封后期限依赖用户填写天数，不是食品安全判断；忘记录开封时只能按未开封保质期。
- 剩菜不参与补货与价格，不会被误当成商品。

**备选**：剩菜建成 `Item` + `StockLot`（否决，制造假商品并污染补货）；开封日期放 `meals`（否决，库存临期视图不完整）；只保留未开封保质期（否决，解决不了每天的真实问题）；自动按购买日期推断开封（否决，不可靠）。

## D43 · 补货只按流水估算，且只做建议

**状态：已定**

**背景**：「快用完自动买」很有吸引力，但家庭消耗不规律、包装单位不一、季节性强。自动下单会重复购买，预测模型会让系统假装知道下个月喝多少牛奶。

**选择**：

- `StockMovement.reason` 固定为 `purchase` / `consume` / `spoil` / `open` / `adjust` / `move` / `return` / `gift`；只有 `consume` 与 `spoil` 计入消耗速度。
- `inventory.usage.rate` 只做窗口内线性平均；有效样本少于 14 天或少于 3 次事件时返回 `insufficient`，不外推、不插值。
- 低库存用物品级 `reorder_at`（基础单位）；未设置就不判断，不设全局魔法阈值。
- 补货建议只读，命中后进入 `meals` 的采购清单；不自动下单、不自动入库。
- 入库由用户确认，走 `inventory.stock.adjust`，默认落到 `Item.home_location_id`；带价格时同事务写价格观测。
- 单位不一致不换算、不合并估算。

**后果**：

- 建议可解释：能看到日均、样本天数、剩余天数与置信度。
- 用户必须认真填 `reason`，否则盘点更正会把预测带偏；UI 要给默认值与快捷入口。
- 季节性、一次性大批量采购仍会不准；系统明确显示「数据不足」而不是编一个天数。
- 没有自动补货，少了一层「忘了买」的自动化，也少了一层重复购买的风险。

**备选**：自动下单/自动入库（否决，家庭场景误购成本高）；按分类或全局阈值（否决，不同物品差异太大）；机器学习预测（否决，样本少、不可解释）；按上次购买时间推算（否决，不知道实际消耗）。

## D44 · 任务支持一次性实例与锚点清单组

**状态：已定**

**背景**：现有 `tasks` 只有「模板 → 实例」，实例必须有模板。但晾衣服提醒、剩菜到期、远行待办都需要「临时一件事」；远行还需要「按出发时间倒排的一组事」。如果都建成周期模板，模板列表会被一次性事项淹没；如果让每个 flow 自己算到期时间，due 逻辑会散落在各处。

**选择**：

- `TaskOccurrence.template_id` 可空，新增 `title` 快照、`subject_type` / `subject_id`、`dedupe_key`；一次性实例由 `tasks.occurrences.create` 创建。
- `dedupe_key` 非空时唯一，重复调用返回已有实例；作用域为家庭。
- `TaskTemplate` 增加 `group_key` 与 `due_offset_minutes`；带 `group_key` 的模板必须 `recurrence=once`。
- `tasks.checklists.instantiate` 以 `anchorAt` 为锚点批量生成，`due_at = anchorAt + due_offset_minutes`；同一 `(template_id, anchor_at)` 幂等。
- 改锚点生成新一组，旧实例保留，由用户完成或跳过，不静默删除。
- 一次性实例与模板实例在列表、完成、跳过、逾期上同构。

**后果**：

- 流程不必自建待办表，也不用把临时提醒伪装成周期模板。
- 迁移需要给已有实例补 `title`，并允许 `template_id` 为空。
- 改期后会出现两组实例，UI 必须提示旧组，否则用户会看到重复待办。
- 清单组只解决「按时间排的待办」，不解决依赖、审批与项目排期。

**备选**：只用周期模板（否决，临时事项污染模板列表）；每个 flow 自己维护待办（否决，due 逻辑分散、无法统一完成）；新建 `checklists` 模块（否决，边界仍属于任务，且会与 `travel` 清单重叠）；引入完整工作流引擎（否决，家庭规模不需要）。

## D45 · 出门与远行清单只提示，不代替确认

**状态：已定**

**背景**：「出门前 30 秒」和「远行清单」很容易滑向自动化：自动锁门、自动断电、自动确认带了东西。但系统无法知道伞是否在包里，也无法验证门锁是否真的锁上；误报比不报更危险。

**选择**：

- 清单是只读聚合 + 用户勾选。勾选只表示「我看到/我做了」，不写成「已带伞」「门已锁」这类事实。
- `smart_home` 只在用户显式确认后执行低风险场景；场景不得包含门锁、加热、燃气、总阀、冰箱断电。
- 不根据门磁、地理围栏自动弹出或自动执行；v1 由用户点按。
- 未知或过期数据标 `stale` / `unknown`，不猜、不输出「不用带伞」。
- 不自动完成任务、不自动改日历、不自动下单。
- ERP 不是安全联锁；燃气、水浸、门锁安全由专用设备负责。

**后果**：

- 清单永远需要人看一眼，不能做到「无感」；但不会在用户没确认时动家里的设备。
- 天气失败、模块缺席时会少几条建议，系统明确显示缺席，而不是假装完整。
- 高风险设备即使接入也保持只读或不可用，功能边界比「全都自动化」窄。
- 以后若要自动锁门/断电，必须新增独立决策与重新认证方案，不能靠 flow 偷偷放开。

**备选**：出门自动执行场景（否决，误判会关掉不该关的设备）；用门磁自动判断已出门（暂缓，无法区分短暂开门）；接摄像头确认（否决，违背隐私边界）；把清单做成强制确认（否决，30 秒场景会被流程拖慢）。
