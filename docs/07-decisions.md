# 07 · 架构决策记录（ADR）

格式：一条决策 = 背景 / 选择 / 后果。状态：`已定`、`待定`、`已废弃`。

---

## D1 · 三层角色与命名

**状态：已定**

- 恒星 **Star**：家中服务器，唯一数据权威。
- 行星 **Planet**：公网无状态中继；对**原生流量**内容零知识；同时作为 Web 的 HTTPS 网关（可见 Web 明文）。
- 卫星 **Satellite**：原生客户端（桌面、Android）与 Web 客户端（浏览器）。

**后果**：所有文档、模块 ID、日志、指标统一使用这三个词；不再引入第四种运行时角色。提到「零知识」时必须限定为「原生流量」。

---

## D2 · 中继传输：WSS + 自研帧

**状态：已定**

**背景**：恒星在 NAT 后，需要主动拨出；卫星在外需要经公网中继；要支持多路复用、背压、大文件。

**选择**：外层使用 WSS（TLS 1.3）+ 自研长度前缀二进制帧；行星只做流级别转发。

**后果**：

- 穿透 HTTP 代理友好；Kotlin 两端统一。
- 需要自己实现并测试流控、保活、重连、公平性。
- 不使用 HTTP/2 或 gRPC，避免行星理解应用语义。

**备选**：WireGuard/Tailscale 打底（放弃，因需要自定义鉴权与零知识中继）；HTTP/2 over tunnel（放弃，行星会看到更多元数据且实现复杂）。

---

## D3 · 原生端到端加密与行星零知识（仅原生）

**状态：已定**

**背景**：行星是公网服务器，可能被攻破；原生客户端的家庭数据不能托付给它。

**选择**：恒星↔原生卫星在一条外层流上建立独立的内层会话；Tink Ed25519 双向认证 + HybridEncrypt 密钥封装 + AES-256-GCM 逐帧加密。

**后果**：

- 行星只能看到原生流 ID、大小、时序。
- 握手与重放保护是安全关键路径，需评审与负例测试。
- LAN 直连也走同一内层会话，保持单一代码路径。
- Web 路径不走内层会话，见 D21/D22。

**备选**：行星对所有流量终止 TLS（否决，原生失去零知识）；自研 Noise（否决，密码学实现风险）。

---

## D4 · SQLite + 薄 JDBC 数据层

**状态：已定**

**背景**：家庭规模数据；需要单文件、易备份、可动态加模块。

**选择**：SQLite（WAL）+ `sqlite-jdbc` + 宿主 `Db` 门面；模块声明 SQL 迁移；不使用 ORM/代码生成。

**后果**：

- 一个 DB 文件 + 附件目录即可备份。
- 单写者；写事务必须短。
- 动态模块无需重新生成宿主代码；迁移由宿主执行。
- 类型安全靠 DTO 映射与测试，不靠编译期 SQL 检查。

**备选**：Exposed/SQLDelight（放弃，动态模块与聚合 schema 不便）；PostgreSQL（放弃，运维成本）。

---

## D5 · 模块 = 服务端 + 客户端代码包

**状态：已定**

**背景**：功能需要可安装；客户端 UI 也要动态。

**选择**：`.hmod` 包含服务端 JAR、桌面 JAR、Android DEX、assets、manifest、签名；服务端与客户端都通过 SPI 注册。

**后果**：

- 真正的动态 UI 能力，不受声明式 DSL 限制。
- Android 动态代码政策/版本耦合/无法沙箱。
- 模块必须与宿主 Compose/Kotlin 版本兼容。
- 卸载/升级在 Android 上需要重启进程。

**备选**：服务端驱动 UI（放弃，表达力受限）；仅服务端模块（放弃，不满足需求）。

---

## D6 · 客户端平台：桌面 + Android + Web

**状态：已定**

**选择**：原生端用 Compose Multiplatform 共享 UI（桌面 JVM + Android ART）；Web 端用固定 TypeScript/HTML/CSS 壳；不包含 iOS。

**后果**：

- 原生 UI 与业务代码共享；Web 页面单独维护（固定壳）。
- 平台能力（相机、文件、通知、密钥存储）需要 `expect/actual` 或接口注入。
- Web 不共享 Compose 代码，只共享 RPC/JSON 契约。
- iOS 需要时再评估，不阻塞 v1。

---

## D7 · 拓扑权威在恒星

**状态：已定**

**背景**：卫星需要知道 LAN 地址与行星列表；行星可能多个。

**选择**：恒星保存并签发拓扑；原生卫星缓存；行星只保留在线注册表；Web 使用当前行星的 HTTPS 网关，不缓存拓扑。

**后果**：

- 单一事实源，冲突少。
- 恒星长期离线时，原生卫星只能使用过期缓存；需要合理 TTL 与手动地址兜底。
- 行星不需要业务数据库。
- Web 地址由行星决定；切换行星时浏览器需换 URL。

---

## D8 · 附件内容寻址

**状态：已定**

**选择**：`files/sha256/ab/cd/<hash>` + 引用表 + GC；DB 只存相对 key。

**后果**：

- 自动去重、完整性校验、备份简单。
- 需要引用计数与 GC；删除业务记录时必须同步删引用。
- 大文件流式处理，不进 DB。

---

## D9 · v1 在线优先

**状态：已定**

**背景**：离线优先与 CRDT 会显著增加复杂度。

**选择**：业务数据以恒星为准；原生卫星只缓存壳数据（拓扑、模块、设置）；Web 不缓存业务数据；无网时展示错误/只读缓存。

**后果**：

- v1 实现简单、一致性强。
- 移动端弱网体验有限；后续可加离线缓存与冲突合并。
- RPC 设计保留幂等键与版本号，为未来同步留余地。

---

## D10 · 模块签名 + 恒星背书

**状态：已定**

**选择**：发布者 Ed25519 签名 `.hmod`；恒星维护信任库；恒星向卫星签发 `ModuleAttestation`。

**后果**：

- 卫星只需信任恒星，不必维护发布者列表。
- 恒星是模块信任的根；恒星被攻破则模块供应链也失守。
- 需要密钥轮换与撤销流程。

---

## D11 · 技术栈与依赖策略

**状态：已定（版本在 M0 锁定）**

**选择**：Kotlin 2.4.x、JDK 25（JVM）、Gradle 9.7.1、Ktor（WSS + HTTPS 网关）、kotlinx.*、Tink 1.7.x、Argon2id（Web 密码）、sqlite-jdbc、Compose Multiplatform/AndroidX Compose、JUnit 5；Web 用 TypeScript 5.x + 原生 HTML/CSS，`tsc` 构建。

**后果**：

- 现代开发体验与跨平台共享。
- 依赖数量高于「纯标准库」路线；需要版本锁定与供应链审查。
- 不引入 DI/ORM/通用 Web 框架，控制复杂度；Web 零运行时依赖。

---

## D12 · 模块 API 稳定面

**状态：已定**

**选择**：`core:star-api`、`core:client-api`、`core:ui` 是唯一稳定 API；从 M1 起主版本冻结；只做兼容新增。

**后果**：

- 第三方模块可长期使用。
- 宿主内部重构自由，但不能泄漏到 API。
- 破坏性变更需要升主版本并保留过渡期。

---

## D13 · Git 与提交规范

**状态：已定**

**选择**：遵循上级 `RULES/COMMIT.md`：

- 原子提交，一项一个 commit。
- 格式 `<括号><动作><括号> <摘要>`：大 `{}`、中 `[]`、小 `()`。
- 每个 commit 后推送 `origin/master`。
- 不 amend、不强推、不改写已推送历史（除非明确要求）。

**后果**：历史可读、可回滚；CI 可按提交粒度追溯。

---

## D14 · 版本策略

**状态：已定**

- **宿主**（star/planet/satellite）：`0.<minor>.<build>`；Android `versionCode` 单调递增。
- **模块**：独立 SemVer（`MAJOR.MINOR.PATCH`）。
- **API**：整数主版本（`api.star` / `api.client`）。
- **协议**：整数主版本 + 次版本（`protoMin/protoMax`）。

**后果**：模块与宿主解耦；升级矩阵需要测试；发布页必须列出兼容范围。

---

## D15 · 不引入 ORM / DI 框架

**状态：已定**

**选择**：手写 SQL + 构造函数注入 + 显式装配。

**后果**：

- 依赖少、启动快、动态模块边界清晰。
- 重复代码略多；用小型宿主工具与约定降低样板。
- 模块不能依赖宿主 DI 容器。

---

## D16 · Android 动态加载方式

**状态：已定（需 spike 验证）**

**选择**：`InMemoryDexClassLoader`（API 26+）+ `d8` 产物；父加载器提供宿主 API/Compose/Tink。

**后果**：

- 避免可写目录执行代码限制。
- ART 无法卸载类；升级/卸载需重启进程。
- 不允许 Android 资源、manifest 组件、原生库。
- Play 政策限制；自有渠道分发。

**备选**：Play Feature Delivery（若上架 Play）；内置模块 + 服务端驱动 UI（保底）。

---

## D17 · LAN 也启用端到端会话

**状态：已定**

**选择**：原生卫星的直连与中继都跑同一内层会话；Web 不适用。

**后果**：

- 单一代码路径；局域网防窃听。
- LAN 上多一层加密开销（家庭规模可忽略）。
- 调试时需要工具解密或使用开发模式日志（不打印密钥）。
- Web 走 HTTPS 网关，不经过内层会话。

---

## D18 · 模块间不共享数据库表

**状态：已定**

**选择**：不建跨模块外键；用逻辑 ID + RPC/事件协作；表名带模块前缀。

**后果**：

- 模块可独立卸载。
- 跨模块一致性由应用层保证；需要定期完整性检查。
- 复杂查询可能需要在宿主层聚合。

---

## D19 · v1 单家庭、单恒星

**状态：已定**

**选择**：一个原生卫星配对到一个恒星；Web 登录到一个 `homeId`；不实现多家庭切换。

**后果**：

- 数据模型与 UI 简化。
- 为未来多家庭保留 `homeId` 与拓扑结构；后续可扩展。

---

## D20 · 模块 v1 限制

**状态：已定**

**选择**：模块不支持原生库、Android 资源、manifest 组件、后台常驻服务、模块间代码依赖、多版本并存；Web 不加载模块，也没有模块自定义页面。

**后果**：

- 降低动态加载与安全风险。
- 复杂能力由宿主提供（相机、文件、通知等）。
- Web 只能使用宿主固定页面；动态模块只影响服务端与原生 UI。
- 未来按需求逐项放开，并补安全评估。

---

## D21 · Web 卫星：行星 HTTPS 网关 + 固定壳

**状态：已定**

**背景**：需要不安装客户端就能访问；浏览器不适合承载 Tink 端到端会话，也不适合动态代码包。

**选择**：

- Web 是完整卫星（可浏览/编辑业务数据）。
- 行星提供 HTTPS 网关，把浏览器请求映射为恒星隧道上的 `WEB_HTTP` 流。
- 恒星提供固定 TypeScript/HTML/CSS 壳与 `/api/web/v1/*` JSON RPC；不加载 `.hmod`。
- 账号密码 + 服务端会话（HttpOnly Cookie）+ CSRF；首次管理员由原生卫星创建。

**后果**：

- 零安装，任何现代浏览器可用。
- 行星终止 TLS，**可见 Web 明文**（见 D22）。
- Web UI 固定；动态模块只有服务端与原生 UI。
- 需要 CSP/CSRF/限流/会话管理/日志脱敏。
- 复用同一套 RPC、权限与业务逻辑。

**备选**：每家庭自建公网 HTTPS（否决，NAT/证书/运维复杂）；浏览器端 E2E（后续评估，密钥管理与体验复杂）；服务端驱动 UI（否决，表达力不足）。

---

## D22 · Web 信任降级：不承诺行星零知识

**状态：已定**

**背景**：HTTPS 网关必须在行星终止 TLS 才能转发 HTTP。

**选择**：明确接受 Web 路径的行星可见明文；原生路径继续零知识；行星不记录正文/Cookie/Authorization；Web UI 提示；高敏感操作建议原生。

**后果**：

- 威胁模型分原生/Web 两条；文档与 UI 不能笼统宣称「行星零知识」。
- 行星被攻破时，Web 数据与会话暴露；原生数据不受影响。
- 需要隐私说明与用户预期管理。
- 后续若做 Web E2E，需单独立项。

**备选**：禁止 Web（否决，不满足需求）；所有流量都走 Web 网关（否决，原生失去零知识）。

---

## D23 · 业务模块文档结构

**状态：已定**

**选择**：

- 一个模块一个文件：`docs/modules/<module-id>.md`；超过 2 页再拆同名文件夹。
- 跨 2 个以上模块的流程放 `docs/flows/`，不塞进模块卡。
- 修改 RPC、表结构或权限时，必须同步更新对应模块卡。
- 模块注册表先用 Markdown 表；M1 后再评估 YAML + CI 校验。
- 模块卡固定包含：目的与非目标、场景、边界、领域模型、权限、RPC/事件、原生/Web UI、数据与迁移、验收、开放问题。

**后果**：

- 模块文档有统一入口与模板，新增模块不依赖口头约定。
- 模块卡只写当前契约；历史取舍仍进 ADR。
- 首批模块卡为 `locations`、`inventory`、`documents`、`tasks`，其余进入路线图时再写。

## D24 · 位置使用多根森林

**状态：已定**

**背景**：家庭位置不只一个「家」。异地恋、老家、工作地会同时存在，单根会把它们强行塞进同一棵树，语义和 UI 都别扭。

**选择**：

- Level 0 允许 0..N 个 `site` 根节点（自己家、老家、工作地、异地恋的住处等）。
- 根之间平级，按 `sort` 排序；v1 根只能重命名、排序、归档，不能挂到其他根下。
- 物品选择器按 Level 0 地点分组；同名房间不冲突。
- 地点之间的物品转移由 `inventory` 的流水记录，`locations` 不存移动历史。

**后果**：

- 需要地点切换器与按地点分组的树形 UI。
- 位置查询从「一棵树」变成「一片森林」；RPC 增加根列表。
- 未来若需要跨地点转移流程，仍由 `inventory` 拥有，不复制到 `locations`。

**备选**：单根 + 虚拟顶层（否决，所有地点被迫同树，语义不自然）；每个地点一个家庭（否决，v1 单家庭）。

---

## D25 · 证件模块 v1 只存掩码

**状态：已定**

**背景**：身份证、护照、银行卡属于高敏感数据；v1 的 DB 文件不加密，Web 路径又经行星明文。

**选择**：

- `identity` 只存掩码、后四位、颁发方、有效期、状态等结构化字段。
- 不存完整证件号/银行卡号、CVV、PIN、磁道/芯片数据。
- 完整信息看扫描件；扫描件归 `documents`，按最高敏感级别保护。
- 查看/下载扫描件写审计；Web 默认脱敏，高敏感操作建议原生。
- 如未来需要完整号码，先增加宿主加密字段能力，再迁移。

**后果**：

- 模块可直接在 v1 落地，不依赖 SQLCipher 或字段加密。
- 用户无法在结构化字段中复制完整号码，需要打开扫描件。
- 导出仍是高敏感操作；备份按最高敏感级别处理。

**备选**：完整号码明文入库（否决）；用 `ModuleConfig` 存 JSON（否决，不可查询、难审计）；v1 上 SQLCipher（后续评估）。

---

## D26 · 证件水印分享按需生成

**状态：已定**

**背景**：证件扫描件外发时需要标明用途和接收方，降低被挪用的风险；不能修改原件，也不应让水印副本长期堆积。

**选择**：

- 水印由 `documents` 统一生成；`identity` 只提供入口、校验记录与扫描件关联，并传上下文。
- 原始文件永远不修改；水印副本默认按需生成、流式返回，不落盘。
- `recipient` 与 `purpose` 必填；水印含接收方、用途、日期、`shareId`。
- 图片纠正 EXIF 方向、叠加后重新编码并剥离元数据；PDF 逐页栅格化后输出扁平化 PDF；拒绝加密 PDF。
- 每次生成新 `shareId`，审计操作者、文档、上下文、接收方、用途、时间、页数。
- 水印是威慑与追溯，不是 DRM；不能阻止截图、裁剪或恶意去除。

**后果**：

- 分享流程不产生新的文档记录，不需要额外的文件 GC。
- 水印生成有 CPU 成本，需要限流、大小/页数限制与超时。
- 需要 PDF 渲染库与中文字体；实现前先做字体与性能验证。
- 如需「我发过给谁」与撤销，后续增加分享记录表，不改变本决策的生成方式。

**备选**：修改原图（否决）；持久化水印副本（暂缓，需派生文件与 GC）；PDF 注释叠加（否决，容易被移除）。

## D27 · 日历与任务分离

**状态：已定**

**背景**：日历和待办都关心日期，但语义不同。把纪念日当任务会让「完成」变得别扭；把家务塞进事件又缺少分派与完成记录。

**选择**：

- `calendar` 拥有事件、纪念日、生日、多日活动与参与者。
- `tasks` 拥有待办、周期、分派、完成记录。
- 日历 UI 只读叠加 `tasks` 的到期项；点击跳转任务详情，不在日历改状态或改期。
- 生日/纪念日 v1 由 `calendar` 建事件，避免和 `members` 双份维护。
- 重复事件服务端展开；v1 不支持单次例外/完整 RRULE；日期不存在时跳过。

**后果**：

- 同一天需要聚合两个 RPC，但所有权清晰。
- 提醒仍需统一通知能力或由 `tasks` 生成，`calendar` 不内置调度。
- 未来若要拖拽改期任务，需要显式调用 `tasks`，不能本地改。

**备选**：日历与任务合并（否决，完成语义冲突）；日历只做展示不存事件（否决，无法管理纪念日）；把生日放 `members`（否决，重复维护）。

---

## D28 · 饮食与库存、任务分离

**状态：已定**

**背景**：菜谱、菜单、采购清单、库存和家务都围绕「吃」，但所有权不同；混在一起会让库存与任务状态难以保持一致。

**选择**：

- `meals` 拥有菜谱、食材、菜单计划、采购清单。
- `inventory` 拥有库存与出入库；`meals` 只引用 `inventory_item_id`，不自动扣减。
- `tasks` 拥有买菜/做饭等任务；`meals` 不复制任务状态。
- `calendar` 可以只读展示当天菜单，但餐次仍归 `meals`。
- 采购清单勾选只表示「已买」，不代表「已入库」。

**后果**：

- 需要显式的库存调整动作，不能靠勾选采购清单自动入库。
- 菜谱食材允许自由文本，降低对库存主数据的依赖。
- 菜单与任务可以在 UI 聚合，但写操作各回各家。

**备选**：库存内置采购清单（否决，菜谱/菜单会反过来依赖库存）；任务内置菜单（否决，完成语义冲突）；自动扣库存（暂缓，容易与实际消耗不符）。

## D29 · 健康记录隐私优先

**状态：已定**

**背景**：健康数据比普通家庭数据敏感；预约、用药提醒、报告文件与健康记录本身分别属于不同模块。

**选择**：

- `health` 只拥有人类健康记录；宠物健康归 `pets`。
- 记录默认 `private`（本人 + `health.admin`）；用户显式改为 `family` 才对家庭成员可见。
- 普通成员只能写自己的记录；代写他人需要 `health.admin`。
- 预约归 `calendar`，提醒归 `tasks`，报告/处方归 `documents`。
- Web 默认只显示摘要；附件下载、导出、详细内容优先原生。
- 健康正文/附件不写日志；v1 依赖磁盘加密，后续再评估字段加密。

**后果**：

- 健康模块需要记录级可见性过滤，不能只靠模块权限。
- 家庭共享需要用户主动选择，默认不透明。
- 导出与附件下载按高敏操作处理，可能要求重新认证。
- 未来若要支持未成年人/成人隐私，需要更细的 ACL 或管理员破窗流程。

**备选**：默认家庭可见（否决，隐私风险）；宠物健康并入 `health`（否决，字段与生命周期差异大）；预约/提醒复制到健康模块（否决，状态会漂移）。

## D30 · 宠物与植物共用档案，护理归任务

**状态：已定**

**背景**：猫狗鸟鱼虫和植物都需要档案与护理记录，但物种差异大；护理又天然是周期任务，容易和 `tasks` 重复。

**选择**：

- `pets` 用一个模块覆盖猫、狗、鸟、鱼、昆虫、植物与其他。
- `kind` 只决定默认 UI 与护理类型，不限制可记录内容。
- 档案、成员关联、护理日志由 `pets` 拥有；护理日志只追加。
- 周期护理计划/提醒归 `tasks`，用 `subject_type="pets.pet"` 指向宠物。
- 食物、药品、耗材库存归 `inventory`；`pets` 不自动扣减。
- 照片、疫苗本、宠物病历归 `documents`。
- 宠物医疗不混入人类 `health`；去世/送养保留历史。

**后果**：

- 需要按 `kind` 做不同的 UI 默认值，但数据模型保持统一。
- 护理提醒不在宠物模块内，避免两套周期引擎。
- 物种专属指标（水温、pH、光照、体重）先放 `metadata_json` 或备注。
- 未来若差异过大，再拆 `plants` 或宠物医疗子模块。

**备选**：猫狗与植物拆两个模块（暂缓，档案结构足够接近）；护理计划内置 `pets`（否决，重复 `tasks`）；宠物健康并入 `health`（否决，权限与生命周期不同）。

## D31 · 智能家居按 Profile / Capability / Driver 三层解耦

**状态：已定**

**背景**：智能家居的设备类型、操作和协议都会持续增加；如果每个设备写一个类、每个动作加一个 RPC、每个协议加一个 enum，核心和 UI 很快会被厂商分支淹没。

**选择**：

- 设备类型是数据化的 `DeviceProfile`，由 `Capability` 组合而成，不写设备类。
- 操作归 `Capability` 的命令与 schema；统一走 `smart_home.commands.execute`，不按设备/动作新增 RPC。
- 协议是 `ProtocolDriver` 模块；核心只依赖 SPI，不出现厂商字段、协议 enum 或 SDK 调用。
- 驱动支持点对点与网关型；统一用 `AdapterInstance` + `DeviceBinding` 表达。
- 状态带 `reported / inferred / optimistic`；命令结果不等于真实状态。
- 新增设备类型优先加 Profile；新增协议装驱动；新增通用能力才改核心。
- 红外码、设备型号、按钮布局是数据；协议实现是代码。
- 门锁 v1 只读，不注册 `unlock`；蓝牙音频由独立音频服务处理。
- 驱动是受信任 `.hmod`，安装时展示发布者与网络/蓝牙/串口需求；高风险命令由策略层拦截。

**后果**：

- 核心代码不随厂商设备增长；新增设备类型和协议可独立交付。
- 需要维护 Profile/Capability 注册表、schema 版本与驱动契约测试。
- 数据化只适合码表、设备组合与 UI 提示；复杂协议仍需写驱动。
- 自动化必须引用稳定的 Capability，不能引用厂商方法。
- 多绑定与状态融合会增加复杂度；v1 只启用主绑定。

**备选**：每个设备一个 Kotlin 类（否决，厂商分支失控）；每个动作一个 RPC（否决，RPC 爆炸）；协议 enum + `when`（否决，新增协议改核心）；所有协议用通用 DSL（否决，复杂协议不可行）；把门锁控制直接接进自动化（否决，安全风险）。

## 决策变更流程

1. 新决策先在本文件加一条（状态 `待定`），写清背景与备选。
2. 影响协议/API/数据的变更，必须同步更新对应文档与测试。
3. 主版本破坏性变更需要迁移方案与过渡期。
4. 被取代的决策标记 `已废弃`，保留历史，不删除。
